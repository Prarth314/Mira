# Design: Mira PMF — Cut to a Voice-to-Dev-Tool Wedge

Mode: Startup

## Problem Statement

Wispr Flow proved voice-to-text dictation can replace typing for a real audience (writers, founders, lawyers). The founder's thesis: Wispr is "purely a typing pipe with zero agency" — voice should be able to *do things* on the computer, not just type.

The current Mira build executes that thesis as a general "voice-controlled OS actuator": Option+Space pops a non-activating overlay, Whisper transcribes locally, the model picks one of five typed actions (`launch_app`, `open_url`, `set_volume`, `describe_screen`, `speak`) and the main process runs it.

Two facts we surfaced this session collapse that thesis:

1. **Wispr is no longer "pure dictation."** Their public "Master Plan" (March 3, 2026) defines their roadmap as `voice input → voice to action → wearables`, and they say they're already prototyping voice actions with power users. The "missing agency" gap Mira was built to fill is on the incumbent's roadmap.

2. **Apple Voice Control is a platform threat, not the paid incumbent.** Almost nobody uses it daily. The actual user behavior we'd take share from is "keyboard + paid dictation + app-native AI." That changes who Mira is competing with.

So the real PMF question is not "is there a missing category?" It is: **can Mira win a narrow wedge before the dictation incumbent and the platform vendors collapse that wedge?**

## Demand Evidence

**Zero direct demand.** N=1 — the founder's own observation. No waitlist, no users, no payment, no behavior data. "I noticed Wispr lacks X" is hypothesis, not demand.

**Indirect signal worth noting:** Wispr Flow itself proves WTP for paid voice tools on Mac. Product Hunt reviews of Wispr cluster on brittleness complaints (Windows stability, CPU/RAM, system integration, privacy) — not "voice on Mac doesn't matter." So the opening is "people want this but current tools are fragile," not "no one cares."

**What we need before more building:** the founder has not interviewed a single Wispr user about what their second wish for the product is. That conversation is the cheapest, highest-information thing remaining.

## Status Quo

What candidate users do today:

- **AI-heavy developers** (Cursor + Claude Code + Linear + Slack all day): keyboard, paste prompts, occasionally Wispr for dictation. Frequent context-switches between editor and chat. Pain point is RSI + flow-state interruption. Spend 30-50 prompts/day.
- **Power-user generalists** (Raycast / Alfred / Karabiner / Hammerspoon stack): scripted keybinds, deep customization. Voice is a curiosity, not a daily driver.
- **Wispr users** (writers, lawyers, founders): voice for typing email/Slack/docs. They want better voice typing, not OS automation.
- **Accessibility users (RSI, motor disability):** Apple Voice Control or Dragon. Real pain, but Apple's product is free, native, and improving — hard wedge to win as a startup.
- **Most people:** mouse + keyboard. Don't perceive any pain.

Cost of the status quo for the AI-heavy developer specifically: real. They are typing the same kinds of prompts dozens of times a day, breaking flow to context-switch, and accumulating RSI risk. That's the only segment where the math says "they would pay to fix this."

## Target User & Narrowest Wedge

**Persona (codex's framing, refined):** Nadia Patel, Staff Engineer at a 25-person SaaS startup. Daily workflow: Cursor / Claude Code / Terminal / Linear / Slack / docs / PR reviews. Issues 30-50 long, precise AI prompts a day. Cares about flow state. Has wrist pain on heavy weeks.

**Wedge:** voice-to-dev-tool prompt router. Hold Option+Space, speak a precise coding instruction ("trace the auth retry bug, patch it, add a regression test, summarize the diff for the PR"), the cleaned-up transcript lands in the frontmost dev tool's prompt field and optionally auto-sends.

**Why she pays:** not because she wants "voice control of her computer." Because she wants to issue 50 long prompts a day without typing them, while preserving the precise-language register that prompts need (filenames, symbol names, code jargon). Mira's value is *flow preservation in a workflow she already does*, not *new behaviors she'd have to adopt*.

**Why this wedge is defensible right now:**

- Off Apple's strongest turf (accessibility / generic OS automation)
- Off Wispr's near-term roadmap focus (their "voice to action" appears to target generic productivity actions, not deep dev-tool integration)
- Apple Intelligence and ChatGPT macOS desktop are not going to ship "voice → editor prompt → auto-send to Cursor" any time soon
- Highest WTP segment per dollar of revenue
- Founder is the persona — fastest dogfood loop possible

## Constraints

- **Solo builder, weekends + nights.** Can't ship a multi-platform agentic OS in v0.1.
- **macOS first.** Existing Whisper / `say` / `osascript` plumbing is Mac-only. Cross-platform is a v0.2+ concern.
- **No native Accessibility / Event Tap helper yet.** True hold-to-talk and keystroke injection both need this. v0.1 must work without it.
- **Pre-launch.** No existing users to break, but also no analytics or evidence loop.
- **Founder's competing project (agentmesh/Relay)** consumes attention. Mira must compound with limited weekly hours.

## Premises

The premises this design rests on. If any are wrong, the recommendation changes.

1. **The current "general voice-controlled OS actuator" framing is too broad to ship as v0.1.** It races multiple platforms and has no demand evidence behind any specific use case.
2. **Wispr is now a direct competitor in the voice-to-action space, not just dictation.** Mira's differentiator must be sharper than "we add agency."
3. **Apple Voice Control is a platform risk, not a real paid-product incumbent.** Most candidate users don't use it daily.
4. **The narrowest wedge with real WTP is voice-to-Claude-Code / voice-to-Cursor for AI-heavy developers.** Other candidates (Apple Shortcuts trigger, accessibility, general power user) are less defensible, less dogfoodable, or directly into Apple's path.
5. **The current Mira codebase is mostly reusable for this wedge.** Provider abstraction, on-device Whisper, IPC backbone, overlay window, conversation owner, action-typing security — all stay. What gets cut is the specific action set, not the infrastructure.
6. **The founder needs real customer interviews (n=10) before building further than the wedge MVP.** Otherwise we're guessing twice in a row.

## Cross-Model Perspective

Codex (independent cold read with web search, ran in this session):

- **Steelman** — "Mira is a low-latency voice execution layer for people who already work through AI all day. Wispr made talking good enough to replace typing. Mira's credible ambition is to make talking good enough to operate real workflows."
- **Gap caught** — Claude wrote "Wispr does voice-to-text dictation beautifully but is purely a typing pipe with zero agency." Codex: "That is no longer true in the present tense. Wispr is already publicly on voice to action."
- **Premise corrected** — Claude wrote "Apple's Voice Control is free and native — hard to beat." Codex: wrong premise. Apple is the platform threat, not the paid incumbent. Test it: interview 10 candidate users, count how many use Voice Control daily. Bet is 0-1 of 10.
- **Wedge call** — voice-to-Claude-Code / Cursor for AI-heavy developers, named Nadia Patel as a persona.
- **Real competitor** — Apple's built-in stack (Voice Control + Shortcuts + Siri + future Apple Intelligence), not Wispr.
- **MVP** — push-to-talk dev prompt router. One action: `send_developer_prompt`. Frontmost-app detection for Claude Code terminal first. Drop generic launch_app / open_url / set_volume / speak / describe_screen as user features. Drop Apple Shortcuts. Drop accessibility. Drop multi-provider story.

Cross-model synthesis: Claude and Codex agree the current scope is wrong, the wedge is voice-to-dev-tool, and the demo should be specific. Codex went further on aggression — it would cut the action set to one. Claude would keep `describe_screen` and `speak` as low-cost retentions. Recommendation below sides with Codex on cuts but keeps a small fallback set for the founder's own dogfood needs.

## Approaches Considered

### Approach A: Voice-to-Dev-Tool Router (codex's MVP, sharpened)

Cut Mira's external-facing scope to **one** primary action: send the cleaned-up transcript as a prompt to the frontmost dev tool. Keep the existing infrastructure (provider abstraction, Whisper, overlay, IPC, conversation owner). Drop the marketing of `launch_app` / `open_url` / `set_volume` as features — keep them as fallback the model can fall back to but don't sell or demo them.

```
                                  ┌─────────────────────────────────┐
   ⌥Space ──► overlay opens       │ Frontmost-app detector          │
   user speaks ──► whisper.cpp ──►│  Cursor      → cursor adapter   │──► paste prompt
                                  │  Claude Code → terminal adapter │     into target,
                                  │  Warp        → terminal adapter │     optionally
                                  │  VSCode      → cursor adapter   │     auto-send
                                  │  (else)      → fallback toast   │
                                  └─────────────────────────────────┘
```

**Effort:** S-M. Most of the heavy work already done — STT, IPC, overlay, action validation, providers. New: frontmost-app detection (`osascript tell application "System Events" to get name of first process whose frontmost is true`), prompt-cleanup pass, per-app paste/send helpers. **2-3 weekends.**

**Risk:** Low-Medium. Native pasting needs Accessibility permission for keystroke injection (the same TYPE action we cut from v0.1). For Claude Code terminal we can paste via clipboard + Cmd+V via osascript without keystroke injection if Accessibility is denied. Cursor has a chat panel that takes plain paste.

**Pros:**
- Sharpest possible demo for a single named persona
- Founder can dogfood every day from day one
- Off Apple's turf
- Off Wispr's near-term roadmap (they target generic actions, not dev tools)
- Highest WTP segment in the candidate pool
- Reuses ~80% of what's already built

**Cons:**
- Pasting reliably across Cursor / Claude Code / Warp / VSCode is integration work, not exciting
- Keystroke injection probably needed eventually → Accessibility permission UX wall
- Niche: TAM is "AI-heavy developers" not "everyone with a Mac"
- Cuts the framing the founder has been building toward for weeks

**Reuses:** All of Phase 1-4 infrastructure. The `Action` discriminated union grows one new variant `send_developer_prompt`. Other actions stay but get demoted in the system prompt and UI.

### Approach B: Voice → Apple Shortcuts Triggers

Don't build actuators ourselves. Become the voice front-end for the user's existing Apple Shortcuts library. Index the user's installed Shortcuts on first run; the model picks the closest match for a spoken intent and runs it via `shortcuts run "Name"`.

**Effort:** S. Small surface — list shortcuts, `shortcuts run`, fuzzy-match on intent. **1 weekend.**

**Risk:** High structural risk. If Apple ever ships "voice trigger for Shortcuts" themselves (they easily could — they own both surfaces), Mira evaporates. Also caps the value at "however good your Shortcuts library is."

**Pros:**
- Compounds with users' existing Mac automation graph
- Tiny diff to current build
- The "OS actuator" thesis gets to live without us building actuators

**Cons:**
- Distribution depends on a niche of users who already invested in Shortcuts
- Defensibility is thin
- Apple is one product launch from collapsing this wedge
- Less dogfoodable for the founder

**Reuses:** Most of the build. Replaces the current 5-action set with one delegated action.

### Approach C: Hold the Current Scope (general voice OS actuator)

Keep building toward "voice control your Mac." Polish all 5 actions. Add wake word and keystroke injection in v0.2. Aim broad.

**Effort:** L. Multi-month. **6-12 weekends.**

**Risk:** High. Races Wispr's roadmap, races Apple Intelligence, races Claude / ChatGPT desktop voice agents. No demand evidence for "voice OS for everyone." Solution-in-search-of-problem pattern.

**Pros:**
- Preserves the founder's existing vision
- Most ambitious

**Cons:**
- No demand evidence
- Multiple platform threats simultaneously
- Worst dogfood economics — most actions are not what the founder personally needs every day
- Highest spend of weekend hours per inch of validated pull

**Reuses:** Everything. But that's because nothing changes.

## Recommended Approach

**Approach A: Voice-to-Dev-Tool Router.**

Why over B: defensibility is real (Apple won't ship voice→Cursor, Wispr won't go this deep into a single workflow), TAM is small but WTP per user is high, dogfood loop is perfect.

Why over C: the current scope is the worst of all worlds — broad enough to lose to platforms, narrow enough to have no fans. Approach A keeps Mira's ambition (voice → action) while collapsing the surface area to something a single weekend can ship and a single user can love.

**What to cut from the marketing surface (not necessarily delete from code):**
- `launch_app` as a sold feature — keep as fallback, don't demo
- `open_url` — same
- `set_volume`, `describe_screen`, `speak` — same
- Multi-provider as a v0.1 selling point — pick Claude as default for prompt-quality reasons; OpenAI stays available but isn't the headline
- The "OS actuator" framing in copy — replace with "voice for Cursor + Claude Code + your terminal"

**What to add:**
- `send_developer_prompt` typed action
- Frontmost-app detector via `osascript`
- Per-app paste adapter (Claude Code terminal first; Cursor chat panel second; Warp third; VSCode fourth)
- Prompt cleanup pass: filenames, symbol names, common code jargon (light dictionary substitution; specifics calibrated by the whisper-accuracy spike below — don't guess what whisper mistranscribes, measure it)
- Optional auto-send (configurable in settings)

**Branch-name reality check:** the in-flight branch is `feat/multi-provider-voice`. Don't rename it — too much commit history. The provider abstraction stays as plumbing (it's correct architecture and zero cost to keep). What changes is the marketing copy and default UI: ship as "voice for Cursor and Claude Code," default to Anthropic Claude in Settings, hide the OpenAI option behind an "advanced" disclosure in the panel.

## Open Questions

- **Cursor's chat-panel focus discipline.** The frontmost app is Cursor, but the focused element might be the editor pane, not the chat input. Paste lands in the wrong place. Per-app adapter probably needs `osascript` accessibility queries to resolve focus before pasting. Measure during the spike.
- **Is the frontmost app even the right paste target?** User might be in Slack but want the prompt to go to Cursor. Maybe `Option+Space` opens overlay, then the user can `Tab` between target apps inside the overlay before releasing. v0.1: frontmost. v0.2: overlay-driven target picker.
- **Apple notarization first-time setup** is a multi-day yak-shave for solo Mac devs (cert provisioning, App-Specific-Password, notarytool teething). Plan for v0.1 to ship unsigned to the first 5 users, v0.1.1 to be the first notarized build.
- **Pricing reconfirm at month +1:** $12/mo is the plan. If churn > 30% in the first cohort, drop to $8 and add a free-tier-with-limits.

## Success Criteria

- **Founder dogfoods Mira for one full week** issuing all Cursor / Claude Code prompts via voice. Counts daily-prompts-via-voice ratio. Target: >50%.
- **5 paying customers within 30 days of v0.1 launch.** Charge from day one. Stripe payment link, no free tier. **Price: $12/mo** (split the diff between Wispr at $15 and Cursor's $20 — positions Mira as a Cursor add-on, not a competitor).
- **Median prompt latency under 2.5s** (utterance end → text in editor). Below that, voice loses to typing.
- **One unprompted user request for a feature you didn't build** in the first 50 users. That's the next wedge expanding from strength.

## Kill Criteria

If any of these hit, stop building Mira and reopen the wedge question. No emotional escape hatch.

- **Interview signal:** fewer than 3 of the first 10 interviewees, unprompted, mention typing fatigue / RSI / flow interruption / repeating long prompts. The wedge is wrong; people don't have this pain in their daily flow.
- **Whisper accuracy:** code-jargon eval (see §Pre-Build Spike below) shows below 80% word-accuracy on a representative dev-prompt corpus. Voice doesn't beat typing for this workflow.
- **Latency:** median utterance-end → text-in-editor exceeds 4s on M1 with `base.en`. Below that bar, voice wastes more time than it saves.
- **Dogfood failure:** founder cannot personally hit >50% voice-prompt ratio after one full week of using Mira on real work. If the founder doesn't reach for it, no one will.
- **Payment:** zero paying customers 30 days after launch, despite 100+ landing-page views. WTP isn't there.

## Pre-Build Spike (must happen before any of the 2-3 weekends)

Two questions are load-bearing for this design and both can be answered in under 90 minutes. Resolve them before opening the editor.

1. **Does clipboard + Cmd+V paste reliably into Cursor's chat input and Claude Code's terminal prompt without Accessibility permission?** 30-minute experiment: write a 20-line script that copies a known string, focuses each target app via `osascript`, sends Cmd+V via `osascript tell application "System Events" to keystroke "v" using command down`, reads back. If yes → no Accessibility wall in v0.1. If no → Accessibility prompt is in the critical path and the timeline grows.
2. **Whisper accuracy on dev-prompt corpus.** 60-minute eval: record yourself reading 30 representative coding prompts you've actually sent in the last week (with filenames, symbol names, library names). Run them through `base.en`. Measure word-accuracy. If <80%, either upgrade to `small.en` (slower, ~2x latency) or rethink the wedge.

If both spikes pass, build. If either fails, revisit before committing weekends.

## Distribution Plan

**v0.1:** GitHub Releases. Manual macOS DMG via electron-builder + codesign + notarize (Phase 5 of the existing implementation plan). Distribution is a single web page: "Mira — voice for Cursor and Claude Code. macOS only. ." Users provide their own Anthropic / OpenAI key.

**v0.2:** add a Stripe payment link and a "register your install" gate so we can talk to users.

**No app store in v0.1.** Mac App Store has restrictions on Accessibility permissions and shell exec that would slow us down.

**No bundled API key** in v0.1. Users bring their own. Avoids becoming a usage-resale business until we have validated PMF on the core voice loop.

## Dependencies

- macOS Accessibility permission flow (already designed for Phase 4 wizard) — required for keystroke injection paste path; clipboard-paste path doesn't need it
- electron-builder + Apple developer cert + notarytool credentials (Phase 5)
- 5-10 candidate users willing to be interviewed (founder must source)
- Decision on default model — recommend Claude Sonnet 4.6 (better at long technical prompts) for v0.1

## The Assignment

**Before writing any more code:** the founder should interview 10 people in the candidate persona (AI-heavy developers, Cursor / Claude Code daily users, ideally with some prior Wispr exposure). One question per call: "Show me the last 5 prompts you sent to Cursor or Claude Code today, and walk me through what you typed and why." Then watch them work for 20 minutes.

That's it. Not "validate the idea." Not "demo Mira." Just sit behind 10 people doing the exact workflow Mira targets and notice what's painful, what's fluid, and what they reach for instead of voice.

If 7+ of those 10 people, unprompted, mention typing fatigue / RSI / flow interruption / repeating long prompts as a real pain — Approach A has its first demand signal. If 0-2 do, the wedge is wrong and the design changes.

Cost: 10 hours over a week. Replaces months of building toward the wrong target.
